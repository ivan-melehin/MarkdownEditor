# Техническое задание на разработку Markdown-редактора ME

## 1. Общая информация

**Название проекта:** Markdown Редактор

**Тип приложения:** веб-приложение — редактор Markdown.

**Назначение:** приложение предназначено для подготовки и проверки текстов в формате Markdown. Пользователь вводит или вставляет текст, форматирует его с помощью панели инструментов, просматривает результат, выполняет автоматическую проверку текста и при необходимости добавляет ссылки на термины из базы знаний Loginom Wiki.

Приложение должно быть простым в использовании, работать локально и не требовать серверной части для основных функций.

---

# 2. Основные требования

Приложение должно обеспечивать:

1. Ввод и редактирование Markdown-текста.
2. Форматирование выделенного текста с помощью панели инструментов.
3. Вставку шаблонов Markdown, если текст не выделен.
4. Предпросмотр результата Markdown.
5. Автоматическое сохранение текста.
6. Отмену и повтор действий.
7. Копирование Markdown в буфер обмена.
8. Импорт и экспорт Markdown-файлов.
9. Проверку текста по набору правил.
10. Подсветку найденных ошибок и потенциально проблемных конструкций.
11. Включение и отключение отдельных проверок.
12. Включение и отключение всех проверок.
13. Проверку терминов из базы знаний Loginom Wiki.
14. Адаптацию интерфейса под разные размеры экрана.

---

# 3. Технологии

Для базовой версии использовать:

* HTML5;
* CSS3;
* JavaScript;
* localStorage.

Допускается использование отдельных JavaScript-библиотек для специализированных функций, если без них невозможно обеспечить требуемое качество, например:

* морфологический анализ русского языка;
* орфографическая проверка;
* пунктуационная проверка;
* fuzzy search.

Такие зависимости должны быть обоснованы и не должны быть необходимы для работы базового редактора.

# 6. Панель Markdown

На панели должны быть кнопки:

### Заголовки

* H1 — `#`
* H2 — `##`
* H3 — `###`
* H4 — `####`
* H5 — `#####`
* H6 — `######`

Обязательно наличие третьего уровня заголовка H3.

### Форматирование

* Жирный:

  ```markdown
  **текст**
  ```

* Курсив:

  ```markdown
  *текст*
  ```

* Жирный + курсив:

  ```markdown
  ***текст***
  ```

* Зачёркнутый:

  ```markdown
  ~~текст~~
  ```

* Inline code:

  ```markdown
  `текст`
  ```

* Блок кода:

  ````markdown
  ```text
  код
  ````

  ```
  ```

### Структурные элементы

* Цитата:

  ```markdown
  > текст
  ```

* Маркированный список:

  ```markdown
  - пункт
  ```

* Нумерованный список:

  ```markdown
  1. пункт
  ```

* Чек-лист:

  ```markdown
  - [ ] пункт
  ```

* Горизонтальная линия:

  ```markdown
  ---
  ```

### Ссылки

Шаблон:

```markdown
[текст](https://)
```

Если выделен текст:

```text
текст
```

после нажатия кнопки получается:

```markdown
[текст](https://)
```

### Изображения

Шаблон:

```markdown
![alt](url)
```

При выделенном тексте:

```markdown
![выделенный текст](url)
```

Также приложение должно обнаруживать конструкции:

```markdown
![alt](url)
```

и проверять их согласно правилам раздела «Проверки».

### Таблица

Кнопка должна вставлять базовый шаблон:

```markdown
| Заголовок 1 | Заголовок 2 |
| ----------- | ----------- |
| Значение 1  | Значение 2  |
```

---

# 7. Работа с выделением

Если пользователь выделил текст и нажал кнопку форматирования, Markdown применяется к выделенному фрагменту.

Пример:

```text
Это важный текст
```

Пользователь выделяет:

```text
важный
```

и нажимает **B**.

Результат:

```markdown
Это **важный** текст
```

Если текст не выделен, кнопка должна вставлять соответствующий шаблон.

Например, кнопка ссылки:

```markdown
[текст](https://)
```

После вставки курсор должен автоматически устанавливается в наиболее подходящее место для ввода.

---

# 8. Отмена и повтор действий

На панели должны присутствовать две отдельные кнопки:

* **Отменить** — Undo;
* **Вернуть** — Redo.

Также должны поддерживаться стандартные горячие клавиши:

* `Ctrl + Z` — отменить;
* `Ctrl + Y` или `Ctrl + Shift + Z` — вернуть.

История должна учитывать:

* ввод текста;
* удаление;
* применение Markdown;
* вставку;
* замену текста;
* добавление ссылок;
* другие изменения редактора.

---

# 9. Копирование

Кнопка **«Копировать»** должна копировать текущий Markdown-текст в буфер обмена.

Копируется именно исходный Markdown:

```markdown
# Заголовок

Это **жирный текст**.

[Ссылка](https://example.com)
```

После успешного копирования пользователь должен увидеть уведомление:

> Текст скопирован.

---

# 10. Очистка

Кнопка **«Очистить»** удаляет весь текст.

Перед удалением рекомендуется показать подтверждение:

> Вы действительно хотите удалить весь текст?

Кнопки:

* Отмена;
* Очистить.

После подтверждения редактор очищается.

---

# 11. Автосохранение

Текст должен автоматически сохраняться в `localStorage`.

Сохранять:

* текст;
* настройки включенных проверок;
* выбранную тему;
* другие пользовательские настройки редактора.

Сохранение не должно выполняться на каждый отдельный символ. Использовать debounce, например 300–1000 мс.

После перезагрузки страницы текст восстанавливается.

---

# 12. Импорт и экспорт

## Импорт

Пользователь может открыть файл `.md`.

Сценарий:

1. Нажимает «Импорт».
2. Выбирает Markdown-файл.
3. Содержимое загружается в редактор.
4. Выполняется проверка текста.

## Экспорт

Пользователь нажимает «Экспорт».

Браузер формирует файл:

```text
document.md
```

и предлагает сохранить его.

---

# 13. Предпросмотр

Справа от редактора должно отображаться визуальное представление Markdown.

Например:

Редактор:

```markdown
# Заголовок

Это **жирный текст**.

- пункт 1
- пункт 2

[Loginom](https://loginom.ru/)
```

Предпросмотр:

# Заголовок

Это **жирный текст**.

* пункт 1
* пункт 2

[Loginom](https://loginom.ru/)

Предпросмотр должен обновляться после изменения текста.

---

# 14. Отображение изображений

В окне предпросмотра изображения Markdown должны отображаться непосредственно как изображения.

Например:

```markdown
![Описание изображения](https://example.com/image.png)
```

В preview должно отображаться само изображение.

При ошибке загрузки изображения рекомендуется отображать понятное уведомление:

> Изображение не удалось загрузить.

---

# 15. Отображение Markdown в редакторе

Основной редактор должен сохранять возможность редактирования исходного Markdown.

Пользователь должен видеть исходный текст:

```markdown
![alt](url)
```

а не визуально отрендеренную картинку.

---

# 16. Отображение пробелов и табуляции

В редакторе должна быть возможность отображать специальные символы пробелов и табуляции по аналогии с VS Code.

Например:

```text
Текст·с·пробелами
→    табуляция
```

Условные обозначения должны визуально отличаться от обычного текста и не влиять на фактическое содержимое документа.

Функция должна включаться и отключаться через меню «Проверки».

---

# 17. Проверка пробелов между числом и %

Нужно обнаруживать конструкции:

```text
15 %
20 %
100 %
```

Пробел между числом и `%` должен подсвечиваться красным.

Корректная конструкция:

```text
15%
20%
100%
```

При наличии ошибки пользователь должен видеть подсветку именно проблемного пробела.

---

# 18. Проверка десятичного разделителя

В тексте должна выполняться проверка десятичных чисел.

Допустимый разделитель:

```text
12.5
0.25
15.75
```

Если используется другой символ:

```text
12,5
12:5
12;5
```

разделитель должен подсвечиваться красным.

При этом необходимо учитывать контекст, чтобы обычные запятые и другие знаки пунктуации не считались ошибками.

---

# 19. Проверка изображений

Должны проверяться конструкции:

```markdown
![alt](url)
```

Если отсутствует `alt`:

```markdown
![](url)
```

подсветить проблемный участок красным.

Также должна проверяться ситуация, когда отсутствует URL:

```markdown
![alt]()
```

или конструкция изображения имеет некорректный формат.

---

# 20. Проверка пробелов в конце строк

Пробелы и табуляции после последнего символа строки должны подсвечиваться красным.

Например:

```text
Текст··
```

где `·` — пробел.

Подсветить именно конечные пробелы.

---

# 21. Подсветка тире и дефисов

Все варианты тире и дефисов должны визуально подсвечиваться тускло-жёлтым цветом.

Проверять как минимум:

```text
-
–
—
```

То есть:

* дефис `-`;
* en dash `–`;
* em dash `—`.

Подсветка должна помогать пользователю визуально различать используемые символы.

---

# 22. Проверка кавычек

В тексте должны различаться:

```text
"текст"
```

и:

```text
«текст»
```

Двойные прямые кавычки:

```text
"
```

подсвечивать красным.

Русские типографские кавычки:

```text
« »
```

подсвечивать тускло-жёлтым.

---

# 23. Специальные термины редактора Loginom

Следующие слова и словосочетания должны подсвечиваться тускло-жёлтым:

```text
Сценарий
Модуль
Пакет
Подключение
Цикл
Узел
Узел-ссылка
Компонент
Производный компонент
```

Поиск должен быть регистронезависимым.

Например:

```text
Узел
узел
УЗЕЛ
```

должны определяться как одно слово.

Необходимо учитывать целостность слова, чтобы часть другого слова случайно не подсвечивалась.

---

# 24. Орфографическая проверка

Выполнять автоматическую орфографическую проверку текста.

Орфографические ошибки:

* подчёркивать красной линией;
* при наведении желательно отображать предполагаемый вариант исправления.

Пример:

```text
аналитическй
────────────
```

При наведении:

```text
Возможно, вы имели в виду:
аналитический
```

Проверка не должна изменять текст автоматически без подтверждения пользователя.

---

# 25. Пунктуационная проверка

Пунктуационные ошибки должны выделяться синим подчёркиванием.

Например:

```text
Текст,который...
     ─
```

При наведении должна отображаться подсказка:

> Возможно, требуется пробел после запятой.

Конкретный механизм пунктуационной проверки должен быть выбран разработчиком с учетом качества проверки русского языка.

---

# 26. Меню «Проверки»

Все проверки должны быть объединены в отдельное выпадающее меню.

На панели:

```text
[ Проверки ▼ ]
```

При нажатии открывается меню:

```text
┌───────────────────────────────────────────┐
│ Проверки                                  │
├───────────────────────────────────────────┤
│ ☑ Показывать пробелы и табуляцию          │
│ ☑ Проверять пробел перед %                │
│ ☑ Проверять десятичный разделитель        │
│ ☑ Проверять изображения                   │
│ ☑ Проверять пробелы в конце строк         │
│ ☑ Подсвечивать тире и дефисы              │
│ ☑ Проверять кавычки                        │
│ ☑ Подсвечивать термины Loginom            │
│ ☑ Орфография                              │
│ ☑ Пунктуация                              │
│                                           │
├───────────────────────────────────────────┤
│ [ Включить все ]       [ Отключить все ]  │
└───────────────────────────────────────────┘
```

Каждая проверка должна включаться и отключаться независимо.

Состояние настроек сохранять в `localStorage`.

---

# 27. Кнопка «Термины»

На основной панели должна присутствовать отдельная кнопка:

```text
[ Термины ]
```

Проверка терминов запускается **по запросу пользователя**, а не обязательно непрерывно после каждого изменения текста.

После нажатия приложение анализирует текущий текст и ищет совпадения с базой знаний Loginom Wiki.

Источник базы знаний:

https://wiki.loginom.ru/

---

# 28. База терминов

Рекомендуемый формат локальной базы:

```json
[
  {
    "id": "analytics",
    "title": "Аналитика",
    "synonyms": [
      "анализ данных",
      "аналитический анализ"
    ],
    "url": "https://wiki.loginom.ru/...",
    "description": "Описание термина"
  }
]
```

Каждый термин должен иметь:

* уникальный ID;
* название;
* URL;
* список синонимов;
* при необходимости описание;
* дополнительные формы слова.

---

# 29. Алгоритм поиска терминов

Не использовать только простое сравнение строк.

Поиск должен учитывать:

1. точное совпадение;
2. регистр;
3. словоформы;
4. однокоренные формы;
5. синонимы;
6. многословные термины;
7. небольшие опечатки.

Например, термин:

```text
Аналитика
```

должен потенциально находиться в:

```text
аналитика
аналитики
аналитикой
аналитический
аналитическая
аналитические
```

Для русского языка рекомендуется использовать морфологическую нормализацию/лемматизацию или stemming.

Для fuzzy search при необходимости допускается использовать Fuse.js либо аналогичное решение.

---

# 30. Поиск многословных терминов

Необходимо искать не только отдельные слова, но и словосочетания.

Например:

```text
машинное обучение
аналитическая платформа
анализ данных
```

должны рассматриваться как единые термины.

Приоритет должен отдаваться более длинному совпадению.

Например:

```text
аналитическая платформа
```

должна иметь приоритет над отдельными совпадениями:

```text
аналитическая
платформа
```

---

# 31. Подсветка найденных терминов

После выполнения проверки найденные потенциальные термины должны подсвечиваться в редакторе.

Например:

```text
Loginom используется для построения аналитических платформ.
                                      └────────────────────┘
```

Подсветка должна отличаться от подсветки ошибок.

Рекомендуется использовать отдельный визуальный стиль, например жёлтую или голубую подсветку.

---

# 32. Выбор термина

При нажатии на подсвеченный фрагмент должно открываться небольшое всплывающее окно.

Например:

```text
┌────────────────────────────────────────┐
│ Найдены подходящие термины          ×  │
├────────────────────────────────────────┤
│ Аналитическая платформа                │
│ Аналитика                              │
│ Аналитическая система                  │
└────────────────────────────────────────┘
```

В верхнем правом углу окна должна находиться кнопка `×`.

---

# 33. Добавление ссылки

Пользователь выбирает термин.

Например:

```text
Аналитическая платформа
```

Программа должна сохранить исходный текст и добавить Markdown-ссылку:

```markdown
[аналитических платформ](https://wiki.loginom.ru/...)
```

Важно: текст внутри ссылки должен остаться именно таким, каким он был в исходном документе.

Например:

```text
аналитических платформ
```

не должен автоматически заменяться на:

```text
Аналитическая платформа
```

---

# 34. Закрытие списка терминов

Если предложенные термины не подходят, пользователь нажимает `×`.

При этом:

* окно закрывается;
* текст не изменяется;
* ссылка не добавляется;
* приложение продолжает работать.

Рекомендуется запоминать отклоненные предложения в рамках текущей сессии, чтобы не показывать одно и то же предложение повторно.

---

# 35. Повторная проверка терминов

После изменения текста пользователь может снова нажать:

```text
Термины
```

Проверка выполняется заново.

Уже превращенные в Markdown-ссылки фрагменты не должны повторно предлагаться для добавления той же ссылки.

---

# 36. Подсветка буквы «ё»

Все буквы:

```text
ё
Ё
```

должны подсвечиваться красным.

Пример:

```text
ещё
  ^
```

При этом текст не должен автоматически заменяться на `е`.

Проверка является только визуальной.

---

# 37. Приоритеты подсветки

Один и тот же символ может попадать под несколько правил.

Необходимо определить приоритеты.

Рекомендуемый порядок:

1. орфографическая ошибка;
2. пунктуационная ошибка;
3. ошибка Markdown;
4. критическая ошибка форматирования;
5. подсветка специальных терминов;
6. подсветка тире/кавычек;
7. подсветка `ё`;
8. подсветка найденного термина.

Если одновременно применяются несколько правил, интерфейс не должен становиться визуально перегруженным.

---

# 38. Tooltip для ошибок

При наведении на подсвеченный участок желательно отображать подсказку.

Например:

```text
┌─────────────────────────────┐
│ Проблема                    │
├─────────────────────────────┤
│ Пробел между числом и %     │
│                             │
│ Рекомендуется: 15%          │
└─────────────────────────────┘
```

Для терминов:

```text
┌─────────────────────────────┐
│ Термин базы знаний          │
│                             │
│ Нажмите для выбора термина  │
└─────────────────────────────┘
```

---

# 39. Светлая и тёмная тема

Приложение должно поддерживать:

* светлую тему;
* тёмную тему.

Переключатель темы располагается на панели.

Выбранная тема сохраняется в `localStorage`.

---

# 40. Адаптивность

Интерфейс должен корректно работать при изменении ширины окна.

Минимально предусмотреть:

### Desktop

```text
┌─────────────────────┬─────────────────────┐
│ Редактор            │ Предпросмотр        │
└─────────────────────┴─────────────────────┘
```

### Планшет

```text
┌─────────────────────────────────────────────┐
│ Редактор                                    │
├─────────────────────────────────────────────┤
│ Предпросмотр                                │
└─────────────────────────────────────────────┘
```

### Мобильный экран

Панель инструментов должна переноситься на несколько строк или становиться горизонтально прокручиваемой.

Кнопки не должны выходить за границы экрана.

---

# 41. Закрепление панели

Верхняя панель инструментов должна иметь возможность быть закрепленной.

При прокрутке большого документа панель остается видимой.

Рекомендуется использовать:

```css
position: sticky;
top: 0;
```

# 42. Горячие клавиши

Обязательно:

* `Ctrl + B` — жирный;
* `Ctrl + I` — курсив;
* `Ctrl + K` — ссылка;
* `Ctrl + Z` — отмена;
* `Ctrl + Y` — возврат.

Дополнительно можно реализовать:

* `Ctrl + Shift + S` — экспорт;
* `Ctrl + O` — импорт;
* `Ctrl + Shift + C` — копирование Markdown;
* `Ctrl + F` — поиск.

---

# 43. Поиск и замена

Добавить функцию поиска и замены.

Возможности:

* поиск;
* замена одного совпадения;
* заменить всё;
* переход между совпадениями.

---

# 44. Статистика документа

В нижней панели отображать:

```text
Символы: 1 245
Слова: 187
Строки: 42
```

При необходимости:

```text
Markdown: OK
Ошибки: 3
Предупреждения: 7
Термины: 12
```

---

# 45. Автоматическая проверка

Проверки, которые не требуют отдельного запроса, могут выполняться автоматически с debounce.

Например:

```text
пользователь печатает
        ↓
ожидание 500 мс
        ↓
запуск проверки
        ↓
обновление подсветки
```

Проверка терминов Loginom должна запускаться отдельной кнопкой «Термины», если иное не будет предусмотрено настройками.

---

# 46. Производительность

Приложение должно оставаться отзывчивым при работе с большими текстами.

Необходимо избегать полного пересоздания DOM после каждого введенного символа.

Рекомендуется:

* debounce;
* кэширование результатов;
* предварительный индекс терминов;
* отдельные проверки;
* запуск тяжелых проверок только при необходимости;
* Web Worker для тяжелой морфологической/орфографической проверки при необходимости.

---

# 47. Сценарий использования №1 — создание текста

1. Пользователь открывает ME.
2. Вставляет текст в редактор.
3. Текст автоматически сохраняется в `localStorage`.
4. Справа отображается предпросмотр.
5. В нижней панели отображается статистика.
6. Активные проверки автоматически анализируют текст.

---

# 48. Сценарий №2 — форматирование

1. Пользователь вводит:

```text
Это важный текст.
```

2. Выделяет `важный`.
3. Нажимает **B**.
4. Получает:

```markdown
Это **важный** текст.
```

5. Предпросмотр автоматически обновляется.

---

# 49. Сценарий №3 — вставка ссылки

1. Пользователь выделяет:

```text
Loginom
```

2. Нажимает «Ссылка».
3. Приложение вставляет:

```markdown
[Loginom](https://)
```

4. Курсор устанавливается в поле URL.

---

# 50. Сценарий №4 — отмена

1. Пользователь применяет жирное форматирование.
2. Понимает, что оно не нужно.
3. Нажимает «Отменить».
4. Форматирование удаляется.
5. Нажимает «Вернуть».
6. Форматирование восстанавливается.

---

# 51. Сценарий №5 — проверка форматирования

Пользователь вводит:

```text
Конверсия составила 15 %.
Цена составила 12,5 рублей.
```

Программа обнаруживает:

```text
15 %
  ↑
```

и:

```text
12,5
  ↑
```

Проблемные участки подсвечиваются красным.

---

# 52. Сценарий №6 — проверка изображения

Пользователь вводит:

```markdown
![alt](image.png)
```

Если `alt` отсутствует:

```markdown
![](image.png)
```

программа подсвечивает `[]` красным.

В preview корректно отображаются изображения с заполненным `alt`.

---

# 53. Сценарий №7 — проверка терминов

Пользователь пишет:

```text
Loginom позволяет создавать аналитические платформы.
```

Нажимает:

```text
Термины
```

Программа:

1. получает текущий текст;
2. нормализует слова;
3. ищет однокоренные формы;
4. ищет многословные совпадения;
5. сравнивает их с базой терминов;
6. подсвечивает:

```text
аналитические платформы
```

Пользователь нажимает на подсвеченный текст.

Появляется:

```text
┌──────────────────────────────────┐
│ Подходящие термины            ×  │
├──────────────────────────────────┤
│ Аналитическая платформа          │
│ Аналитика                        │
└──────────────────────────────────┘
```

Пользователь выбирает:

```text
Аналитическая платформа
```

Получает:

```markdown
Loginom позволяет создавать [аналитические платформы](URL).
```

---

# 54. Сценарий №8 — термин не подходит

1. Пользователь нажимает на подсвеченное слово.
2. Появляется список кандидатов.
3. Ни один вариант не подходит.
4. Пользователь нажимает `×`.
5. Список закрывается.
6. Текст остается без изменений.

---

# 55. Сценарий №9 — отклонение термина

Если пользователь неоднократно отклоняет конкретный вариант, приложение может запомнить это решение.

Например:

```text
ignoredTerms
```

хранится в `localStorage`.

Это не должно менять базу знаний и должно быть локальным пользовательским параметром.

---

# 56. Сценарий №10 — восстановление после перезагрузки

1. Пользователь вводит текст.
2. Закрывает вкладку.
3. Открывает приложение снова.
4. Приложение загружает текст из `localStorage`.
5. Восстанавливает настройки проверок.
6. Восстанавливает тему.
7. Текст доступен для дальнейшего редактирования.

---

# 57. Сценарий №11 — работа на мобильном устройстве

1. Пользователь уменьшает ширину окна.
2. Редактор перестраивает интерфейс.
3. Панель инструментов переносится.
4. Редактор и preview располагаются вертикально.
5. Все кнопки остаются доступными.
6. Всплывающие окна терминов не выходят за границы экрана.

---

# 58. Требования к архитектуре проверок

Проверки должны быть реализованы независимо друг от друга.

Рекомендуемая архитектура:

```text
ValidationManager
│
├── WhitespaceValidator
├── PercentValidator
├── DecimalSeparatorValidator
├── ImageValidator
├── TrailingWhitespaceValidator
├── DashValidator
├── QuoteValidator
├── LoginomTermsValidator
├── SpellingValidator
└── PunctuationValidator
```

Каждый валидатор должен возвращать стандартизированный результат:

```js
{
    start: 100,
    end: 105,
    type: "error",
    rule: "percent-space",
    message: "Между числом и % не должно быть пробела"
}
```

Это позволит независимо включать и отключать проверки.

---

# 59. Требования к базе терминов

Для производительности база терминов должна индексироваться.

Рекомендуемая схема:

```text
Wiki
 ↓
парсер/экспорт
 ↓
terms.json
 ↓
индексация
 ↓
нормализованные формы
 ↓
обратный индекс
 ↓
поиск
```

Не рекомендуется обращаться к Wiki для каждого слова текста.

Предпочтительный вариант — периодически формировать локальный `terms.json`.

---

# 60. Требования к качеству поиска терминов

Поиск должен минимизировать ложные срабатывания.

Приоритет:

```text
точное совпадение
        ↓
словоформа
        ↓
синоним
        ↓
однокоренное слово
        ↓
fuzzy matching
```

Для многословных терминов приоритет имеет более длинное совпадение.

Например:

```text
машинное обучение
```

имеет приоритет над отдельными:

```text
машинное
обучение
```

---

# 61. Безопасность Markdown

При отображении preview необходимо безопасно обрабатывать HTML и внешнее содержимое.

Нельзя позволять введенному пользователем Markdown выполнять произвольный JavaScript.

Необходимо:

* санитизировать HTML;
* блокировать опасные конструкции;
* безопасно обрабатывать ссылки;
* безопасно обрабатывать изображения;
* не выполнять `<script>` из пользовательского текста.

---

# 62. Требования к UI/UX

Интерфейс должен быть минималистичным и не перегруженным.

Основные действия должны быть доступны непосредственно с панели.

Второстепенные функции помещаются в выпадающие меню.

Рекомендуемая структура:

```text
[Markdown-инструменты]

[Отменить] [Вернуть]

[Проверки ▼]

[Термины]

[Копировать] [Импорт] [Экспорт] [Очистить]

[Тема]
```

# 66. Главный принцип проекта

ME должен не просто позволять писать Markdown, а выступать как **инструмент подготовки и редакторской проверки технического текста**.

При этом приложение не должно самостоятельно менять содержимое документа без явного действия пользователя.

Все автоматические проверки должны работать прежде всего как визуальные подсказки:

```text
обнаружить → подсветить → объяснить → предложить исправление → пользователь принимает решение
```

А добавление терминов из базы знаний должно работать по принципу:

```text
найти → предложить → пользователь выбирает → добавить Markdown-ссылку
```

Это позволит сохранить контроль над итоговым текстом за пользователем.
